## Как обновлять код

```
clasp login --no-localhost          # в новой сессии: ссылку Ирине, она вернёт redirect-URL
cd apps-script && clasp push        # код → Apps Script (триггеры подхватывают сразу)
clasp deploy -i <deploymentId>      # обновить БОЕВОЙ deploy, URL сохраняется
```
⚠️ **`clasp push` ВСЕГДА перед `clasp deploy`, с паузой.** Один раз deploy собрался из старого
кода, и я ошибочно решил, что сломан разбор заказа.
⚠️ Голый `clasp deploy` создаёт НОВЫЙ URL — тогда придётся менять адрес вебхука в Тильде.
Триггеры работают от свежего кода (`push`), боевой вебхук — от закреплённого deploy.

## Как это работает сейчас

**Источник правды — YClients.** Сайт только отображает; в Тильду уходит АБСОЛЮТНЫЙ остаток,
не разница, поэтому потерянный сигнал выравнивается следующим прогоном.

**Поток A — магазин → сайт (остатки и цены).**
- Каждые 5 минут: один запрос `/storages/transactions` (окно 3 суток). Помним прошлый список
  «номер операции → товар» в `TX_SEEN` и берём **появившиеся И исчезнувшие** номера —
  исчезнувший = операцию удалили, товар надо вернуть на сайт. Доп. запросов не требует.
- Ловит ЛЮБОЕ движение по складу магазина 637823 (продажа, списание, приход, перемещение,
  инвентаризация) — по типу не фильтруем. Расходники (637822) не трогаем.
- ⚠️ **Изменение ЦЕНЫ движения не создаёт** → пятиминутка его не видит. Цену подтягивает
  только полная сверка, поэтому она **каждый час** (04:00 — просто один из 24, отдельного
  ночного прогона нет).
- Названия и артикулы НЕ синхронизируем (в Тильде продающие названия Ирины). Проверено:
  полный прогон 500 товаров исправил 14 цен и не тронул ни одного названия.
- **Новые карточки Тильда создаёт сама** («создавать новые товары» ВКЛ) — с названием и ценой
  из YClients и с проставленным External ID, без категории; Ирина дозаполняет.

**Поток B — сайт → магазин (заказ → списание).**
1. Вебхук корзины → `doPost` → **ОДИН** `POST /storage_operations/operation/{company}`
   с документом и всеми позициями сразу → списание атомарно, «половины» быть не может.
2. Подпись каждой позиции — `PUT /storage_operations/goods_transactions/{company}/{tx_id}`.
3. Подпись документа — `PUT /storage_operations/documents/{company}/{doc}`.

Шаги 2–3 косметические: если они сорвутся, склад УЖЕ изменён верно, не хватает только
комментария — он добирается очередью повторов. Сбой подписи не может испортить остаток.
- Операция: **`type_id=1` (продажа) с `cost=0`** → финансовая операция НЕ создаётся, выручка
  не задваивается (Ирина проводит её статьёй дохода). Подтверждено на боевом.
- Подпись: **«Заказ из интернет-магазина El'Naturel Shop №<номер>»**.
  ⚠️ **Номер ведём МЫ** (`ORDER_SEQ_NEXT`), а не берём из вебхука: Тильда свой «порядковый номер
  заявки» не передаёт — приходит только внутренний длинный `orderid`, а `systranid` всегда 0
  (проверено на боевом). Счётчик засеян числом 233 (у Ирины на 25.07 был заказ 232), следующий —
  234. Разошлось с нумерацией Ирины → поправить `?action=setup&ORDER_SEQ_NEXT=<номер>`.
  Внутренний id Тильды в комментарий не пишем (её решение — один номер), но он есть в журнале.
- Идемпотентность по `tranid` (Script Property `order_<tranid>`), повтор заказа не задваивает.
- Ответственный мастер — Ирина (969478): YClients требует реального сотрудника.

## Нагрузка и защита от перегруза

**Крутится всего три триггера:** обновление остатков каждые 5 мин, полная сверка каждый час,
чистка журнала раз в месяц. Больше по расписанию ничего.

Замеры из журнала (не оценки):

| Что | Раз в сутки | Длительность | К YClients | К Тильде |
|---|---|---|---|---|
| Обновление сайта, движений не было | ~280 | 2,4 с | 1 | 0 |
| Обновление сайта, была продажа | единицы | 6–9 с | 1 + по товарам | ~6 |
| Полная сверка | 24 | 23–26 с | ~8 | ~8 |
| Заказ с сайта | по факту | 0,2 с | 1 + подписи | 0 |

**Итого ≈650 обращений к YClients и ≈200 к Тильде в сутки.**
- **YClients: 5 запросов в СЕКУНДУ** — официальный лимит. Мы делаем 650 за СУТКИ.
- **Apps Script:** 20 000 внешних запросов/сутки (у нас ~3%), 90 мин работы триггеров/сутки
  (у нас ~22 мин). Финансовая интеграция — отдельный проект, квоты Google не складываются.
- **Тильда:** точной цифры нет, лимит виден только по ответу «Many requests».

⚠️ **Опасен не суточный объём, а ПИК** (замечание Ирины). Реальные объёмы: заказ с сайта
1–10 позиций, ПРИХОД накладной 10–150 позиций. Четыре уровня:

1. **Умное чтение под объём.** До 20 изменившихся товаров читаем по одному (`/goods/{id}` —
   быстро на малых числах). Больше 20 → постраничный каталог: **~8 запросов независимо от
   количества**, что 30 позиций, что 150. Приход на 150 позиций = 15–20 с вместо 1,5–2 мин.
   ✅ Проверено на боевом (порог временно опускали до 1) — товары прочитаны каталогом и ушли
   в Тильду за 8,7 с; порог возвращён на 20, следы теста убраны.
2. **Ограничитель скорости `ycPace_`** — минимум 250 мс между обращениями к YClients,
   то есть не быстрее 4 запросов в секунду при потолке 5.
3. **Замок `LockService`** — пятиминутка и полная сверка никогда не идут параллельно (раз в час
   они совпадают). Второй прогон ждёт до 2 минут, потом пропускает — повторится через 5 минут.
   ✅ Проверено: два одновременных прогона встали в очередь (первый 25,9 с, второй 46,8 с,
   из них ~21 с ожидания).
4. **Повтор при отказе.** YClients ответил **429** → ждём 3 → 9 → 20 с и повторяем.
   Сбой 5xx повторяем ТОЛЬКО для чтения: повтор POST создания продажи мог бы задвоить операцию.
   У Тильды тот же приём (10 → 20 → 30 с на «many requests»).

Зачем четвёртый, если есть первые три: они прикрывают только НАШИ запросы. Финансовая
интеграция — отдельная программа, наш замок на неё не действует; от чужого влияния и сбоев
YClients спасает только повтор.

⚠️ **`doPost` (приём заказа) намеренно НЕ ждёт замка** — Тильде нужен быстрый ответ,
заказ важнее ровности графика. Он делает несколько запросов и прикрыт повтором при 429.

⚠️ **Принято осознанно:** приход на 300+ позиций Ирина при необходимости оформит частями.
Даже одним куском данные не потеряются — что не успеет уехать, догонит часовая сверка.

## Грабли — не повторять

- ⚠️ **Вебхук Тильды активируется ТОЛЬКО при сохранении** и лишь если приёмник ответил 200
  за 5 СЕКУНД на проверочный `test=test`. Не успел — вебхук в списке есть, выглядит
  подключённым, но НЕ срабатывает никогда (потеряли на этом полдня). Лечение: `test=test`
  обрабатывается первым же действием `doPost`, до таблиц, почты и YClients (1,7–2,1 с).
  **Пересохранения мало — помогло только пересоздание сервиса с нуля.** После любой правки,
  влияющей на скорость ответа, вебхук пересоздать.
- ⚠️ **Формат вебхука — form-urlencoded с КВАДРАТНЫМИ СКОБКАМИ**, не JSON-строка:
  `payment[products][0][externalid]=_11204288`, `[quantity]` — количество,
  а **`[amount]` — это СУММА, не количество** (ловушка). `payment[systranid]` всегда 0.
  Разворачивает `unflattenParams_`; JSON-тело тоже поддерживается.
- ⚠️ **YClients игнорирует `comment` при СОЗДАНИИ операции** — только отдельным PUT.
  Документу нужны `type_id`, `storage_id`, `create_date` (с ПОЛНЫМ временем), позиции — ПОЛНОЕ
  тело (`good_id`, `amount`, `cost_per_unit`, `discount`, `cost`, `operation_unit_type`,
  `master_id`, `document_id`). `PATCH` не поддерживается (405).
- ⚠️ **`GET /storages/transactions` ВСЕГДА отдаёт комментарий позиции пустым.** Читать надо
  `GET /storage_operations/operation/{company}/{doc}`. Дважды из-за этого ошибочно решил,
  что подпись не ставится.
- ⚠️ **У CommerceML Тильды есть лимит частоты** («Many requests»). Медленная версия невольно
  делала паузы, быстрая упёрлась сразу. Лечение: партии по 250, пауза 8 с между партиями,
  повтор `checkauth` 10/20/30 с (только на «many request», прочие ошибки падают сразу),
  ожидание разбора файла — опрос каждые 1,5 с, максимум 45 с.
- ⚠️ **Остаток в Тильде живёт своей жизнью до синхронизации:** она уменьшает его у себя при
  оформлении заказа, а удаление заказа НЕ возвращает. Возвращать только в YClients.
- ⚠️ **Мои промахи — правила из них:** фильтр «это ли корзина» молча съел первый настоящий
  заказ → **никогда не отбрасывать входящие данные без следа**; неполный обход витрины
  (упал один запрос) дал ошибочное «10 товаров нет на сайте» вместо 2 → **выводы только
  на полных данных, при сбое повтор**; чистка по слову `test` стирала следы проверки Тильды →
  шаблон сужен до `TEST-|PROBE|PROD-|CHECK-`.

## Открытые вопросы и риски

- ⚠️ **Диагностический `doGet` открыт наружу**, гейтится захардкоженным `DIAG_SECRET_`
  (web app анонимный — иначе Тильда не сможет постить). Кто знает секрет и URL — может
  перезаписать Script Properties (`setup`), создать операцию (`testOp`, меняет остаток),
  почистить журнал. Секрет в коде, репозиторий приватный; боевой deploy закреплён на версии
  без части действий. **После обкатки — удалить `setup`/`delDoc`/`testOp` или перенести секрет
  в Script Property.**
- ⚠️ **У токена нет прав удалять складские документы** (405/403) — чистка ошибочных операций
  только руками Ирины в YClients. Любая наша ошибочная операция сама не откатится.
- **Остаток заполнен лишь у 43 товаров из 700** (цена — у 377), master-список 500. Само по себе
  норма (много неактуальных позиций), но для большинства карточек на сайт уходит остаток 0.
  Если что-то реально в наличии, а в YClients ноль — сайт это скроет. Сверить при случае.
